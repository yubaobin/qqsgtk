# 版本管理与发布规范

本文档规定 Khala 项目的版本号管理、分支策略、发布流程及回滚机制。

---

## 一、版本号规范

采用 [语义化版本](https://semver.org/lang/zh-CN/)（SemVer）：

```
MAJOR.MINOR.PATCH
```

| 位置 | 递增条件 | 示例 |
|------|----------|------|
| **MAJOR** | 不兼容的 API 变更 | `1.0.0` → `2.0.0` |
| **MINOR** | 向下兼容的功能新增 | `1.0.0` → `1.1.0` |
| **PATCH** | 向下兼容的问题修复 | `1.0.0` → `1.0.1` |

### 1.1 版本号与 Git 提交类型对应

| 提交类型 | 版本影响 |
|----------|----------|
| `feat` | MINOR |
| `fix` | PATCH |
| `perf` | PATCH |
| `build(deps)` | PATCH |
| `BREAKING CHANGE` | MAJOR |

### 1.2 预发布版本

```
1.0.0-alpha.1   # 内测版
1.0.0-beta.1    # 公测版
1.0.0-rc.1      # 候选发布版
```

## 二、分支策略

采用 **Git Flow 简化版**：

```
main        ─────●─────●─────●─────●─────●─────●  （生产分支，仅接受合并）
                  ↑     ↑           ↑     ↑
release/1.0.0 ───●─────●  （发布分支，仅修复 Bug）
                  ↑
feature/task-123 ─●─────●─────●  （功能分支）
                  ↑
hotfix/fix-001 ───●─────●  （热修分支）
```

### 2.1 分支说明

| 分支 | 来源 | 合并目标 | 生命周期 |
|------|------|----------|----------|
| `main` | - | - | 永久 |
| `feature/{id}` | `main` | `main` | 功能开发完成后删除 |
| `release/{version}` | `main` | `main` + Tag | 发布后删除 |
| `hotfix/{id}` | `main` | `main` + Tag | 发布后删除 |

### 2.2 分支命名

```
feature/task-123-add-approval-node
hotfix/fix-456-login-timeout
release/1.2.0
```

## 三、发布流程

### 3.1 常规发布

```
1. 从 main 切出 release/{version} 分支
2. 在 release 分支上修复测试发现的问题（仅 Bug 修复，不新增功能）
3. 更新版本号（pom.xml / package.json）
4. 更新 CHANGELOG.md
5. 合并 release 分支到 main
6. 在 main 分支打 Tag：git tag -a v1.2.0 -m "Release 1.2.0"
7. 推送 Tag：git push origin v1.2.0
8. 触发 CI/CD 流水线构建并部署
9. 验证生产环境
10. 删除 release 分支
```

### 3.2 热修复发布

```
1. 从 main 切出 hotfix/{id} 分支
2. 修复问题并测试
3. 更新 PATCH 版本号
4. 合并到 main 并打 Tag
5. 触发部署
6. 删除 hotfix 分支
```

## 四、灰度发布

### 4.1 策略

| 策略 | 适用场景 | 说明 |
|------|----------|------|
| **按流量比例** | 通用 | 5% → 20% → 50% → 100% |
| **按用户标识** | 特定用户验证 | 白名单用户先体验 |
| **按地域** | 分区域验证 | 先灰度非核心区域 |
| **按设备/版本** | App 发布 | 按 App 版本号灰度 |

## 五、回滚机制

### 5.1 自动回滚条件

| 条件 | 说明 |
|------|------|
| 健康检查失败 | 新版本 Pod 持续未就绪 |
| 错误率飙升 | 5xx 错误率 > 1% |
| P99 延迟翻倍 | 响应时间超过基线 2 倍 |
| 业务指标异常 | 核心接口成功率下降 |

### 5.3 数据库回滚

> **数据库变更不可回滚**，必须通过补偿脚本或下版本修复。

- 发布前必须准备好 **回滚 SQL**（如删除新增字段需先确认无数据依赖）
- 破坏性变更必须分两步：先加新字段 → 下版本再删旧字段

## 七、发布检查清单

- [ ] 所有测试通过（单元测试、集成测试、接口测试）
- [ ] 代码审查通过（>= 2 人 approve）
- [ ] 版本号已更新
- [ ] CHANGELOG 已更新
- [ ] 数据库变更脚本已准备并通过测试
- [ ] 配置变更已同步至各环境
- [ ] 回滚方案已确认
- [ ] 监控告警已配置
- [ ] 灰度比例已设定
- [ ] 发布通知已发送（技术群 + 业务方）

---

## 八、禁止事项

1. **禁止直接提交到 `main` 分支**，必须通过 MR/PR 合并
2. **禁止在 release 分支上新增功能**，仅允许 Bug 修复
3. **禁止跳过测试直接发布**
4. **禁止无 Tag 直接部署到生产**
5. **禁止回滚时仅回滚代码不回滚配置**
