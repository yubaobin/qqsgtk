# 代码审查规范

本文档规定 Khala 项目的代码审查流程、检查清单及审查标准，保障代码质量与知识共享。

---

## 一、审查流程

### 1.1 基本流程

```
开发者提交 MR/PR
        │
        ▼
   CI 自动化检查（编译、测试、代码规范）
        │
        ├── 失败 → 开发者修复，重新提交
        │
        └── 通过
              │
              ▼
         分配审查人（自动/手动）
              │
              ▼
         审查人审查（代码 + 测试 + 文档）
              │
              ├── 有意见 → 开发者修改 → 重新审查
              │
              └── 通过
                    │
                    ▼
               合并到目标分支
```

### 1.2 审查人分配

| 变更范围 | 审查人要求 |
|----------|------------|
| 单模块内部改动 | 1 名同模块开发者 + 1 名模块负责人 |
| 跨模块改动 | 涉及模块各 1 名代表 + 架构师 |
| 公共组件改动 | 2 名以上使用者代表 + 架构师 |
| 配置/基础设施改动 | 运维负责人 + 架构师 |

## 二、审查检查清单

### 2.1 功能性检查

- [ ] 代码实现了需求描述的全部功能点
- [ ] 边界条件处理正确（空值、越界、异常输入）
- [ ] 并发场景处理正确（线程安全、竞态条件）
- [ ] 业务逻辑与领域规则一致
- [ ] 不存在逻辑死循环或无限递归

### 2.2 安全性检查

- [ ] 无 SQL 注入风险（使用 `#{}` 占位符）
- [ ] 无 XSS 风险（用户输入已转义）
- [ ] 敏感信息未硬编码（密码、密钥使用配置中心）
- [ ] 权限校验到位（方法级别、数据范围级别）
- [ ] 无敏感数据明文日志输出

### 2.3 性能检查

- [ ] 无 N+1 查询问题
- [ ] 大数据量操作已分页
- [ ] 循环内无重复计算或 I/O 操作
- [ ] 缓存使用合理（命中率、一致性）
- [ ] 无内存泄漏风险（线程池、连接池正确关闭）

### 2.4 代码质量检查

- [ ] 命名符合规范（类、方法、变量见名知意）
- [ ] 方法长度 <= 50 行，圈复杂度 <= 10
- [ ] 无重复代码（DRY 原则）
- [ ] 异常处理完整（不吞异常、不抛裸异常）
- [ ] 日志记录充分（关键流程有日志）

### 2.5 测试检查

- [ ] 新增代码有对应的单元测试
- [ ] 测试覆盖核心分支（正常、异常、边界）
- [ ] 测试用例命名清晰（Given-When-Then 风格）
- [ ] 集成测试通过

### 2.6 文档检查

- [ ] 接口变更已更新 API 文档
- [ ] 复杂逻辑有注释说明
- [ ] 配置变更已同步配置中心

## 三、审查标准

### 3.1 审查意见分级

| 级别 | 含义 | 处理要求 |
|------|------|----------|
| **阻塞（Block）** | 必须修复，否则不能合并 | 开发者必须修改 |
| **建议（Suggestion）** | 推荐改进，但非强制 | 开发者可选择性接受 |
| **疑问（Question）** | 需要澄清的设计或实现 | 开发者需回复解释 |
| **赞扬（Praise）** | 好的实践值得鼓励 | 无需处理 |

### 3.2 阻塞级问题清单

以下问题属于阻塞级，必须修复：

1. 功能缺陷（未实现需求或实现错误）
2. 安全漏洞（注入、越权、信息泄露）
3. 空指针风险（未判空的链式调用）
4. 资源泄露（数据库连接、文件流未关闭）
5. 错误的异常处理（吞异常、System.exit）
6. 并发安全问题（共享可变状态无同步）
7. 测试未通过或核心流程未覆盖

## 四、自动化检查

### 4.1 CI 流水线检查项

```yaml
# .github/workflows/ci.yml（示例）
name: CI

on: [pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Compile
        run: mvn clean compile

      - name: Unit Tests
        run: mvn test

      - name: Code Coverage
        run: mvn jacoco:report
        # 要求 Service 层 >= 80%，Util >= 90%

      - name: SpotBugs
        run: mvn spotbugs:check

      - name: Checkstyle
        run: mvn checkstyle:check

      - name: SonarQube Scan
        run: mvn sonar:sonar
```

### 4.2 自动化工具配置

| 工具 | 用途 | 失败阈值 |
|------|------|----------|
| Checkstyle | 代码格式规范 | 0 个错误 |
| SpotBugs | 潜在 Bug 检测 | 0 个 High/Medium |
| SonarQube | 代码质量综合评分 | Quality Gate 通过 |
| JaCoCo | 测试覆盖率 | Service >= 80%, Util >= 90% |

## 五、审查沟通规范

### 5.1 提意见原则

- **对事不对人**：评论代码，不评论人
- **解释原因**：不仅说"应该改"，还要说"为什么"
- **提供方案**：最好能给出修改建议或示例代码
- **区分优先级**：明确是阻塞还是建议

### 5.2 良好示例

```
阻塞：这里直接使用 userId 查询，未校验当前用户是否有权限查看
该任务。建议增加数据范围校验：

    if (!taskService.hasPermission(currentUserId, taskId)) {
        throw new AuthException("无权限查看该任务");
    }
```

```
建议：这个方法有 80 行，建议拆分为 3 个小方法：
- validateInput()
- buildEntity()
- saveAndNotify()
```

### 5.3 不良示例

```
❌ "写得不好，重写"
❌ "这里有问题"
❌ "你不懂这个吗？"
```

## 六、审查效率

### 6.1 MR/PR 规模

| 指标 | 建议值 | 上限 |
|------|--------|------|
| 代码行数 | < 400 行 | 800 行 |
| 文件数 | < 10 个 | 20 个 |
| 功能点 | 1 个 | 2 个 |

> 超过上限应拆分提交。

### 6.2 审查时效

| 优先级 | 响应时间 |
|--------|----------|
| 阻塞 Bug 修复 | 2 小时内 |
| 常规功能开发 | 24 小时内 |
| 文档/配置变更 | 48 小时内 |

## 七、特殊场景

### 7.1 紧急修复

生产故障热修复可简化流程：

1. 口头同步技术负责人
2. 审查可事后补（24 小时内）
3. 必须保留修复记录和复盘文档

### 7.2 重构审查

纯重构（无功能变更）应：

- 单独提交，与功能变更分离
- 提供重构前后的对比说明
- 确保测试用例全部通过（行为不变）

---

## 八、禁止事项

1. **禁止未经审查直接合并代码**
2. **禁止审查人只点 approve 不看代码**
3. **禁止开发者不回复审查意见直接合并**
4. **禁止在审查中人身攻击或情绪化表达**
5. **禁止绕过 CI 检查强制合并**
