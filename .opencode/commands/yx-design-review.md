## 执行角色
架构师

## 执行粒度
每次概要设计完成后执行一次

## 前置条件
- 需求规格文档存在（`khala-spec/rd/requirements/` 目录存在）
- 概要设计文档已生成（`khala-spec/rd/design/changes/` 目录存在，由 `/yx:design` 生成）
- 4+1视图图已生成（`khala-spec/rd/design/changes/diagrams/` 目录下视图图文件存在）
- 设计概览文档已生成（`khala-spec/rd/design/changes/design-overview.md` 存在）

## 核心目标
对 `/yx:design` 生成的概要设计文档进行全面评审，确保设计合理、合规、可落地。**发现问题当场修改，修改后重新验证。**

---

## 步骤

### 1. 读取输入文档
```
1. 读取概要设计文档目录（khala-spec/rd/design/changes/），包括 design-overview.md 和版本目录增量设计文档
2. 读取需求规格文档目录（khala-spec/rd/requirements/）
3. 读取知识库速查规范（khala-spec/.rules/backend/ 和 khala-spec/.rules/frontend/），用于合规校验
4. 读取架构与设计规范文档（khala-spec/wiki/architecture/ 和 khala-spec/wiki/design/），如有
5. 读取 PBC 能力文件（khala-spec/rd/references/pbc/），用于 PBC 引用一致性校验，如有
```

### 2. 完整性审查
逐章检查概要设计文档是否包含以下必要章节，并评估每个章节的内容是否充实（非占位符、非空泛描述）：

| 章节 | 必须存在 | 审查要点 |
|------|----------|----------|
| 设计概览文档 | ✅ | `design-overview.md` 是否存在，是否包含引言、系统目标与约束、技术路线、架构设计（引用5个视图图链接）、安全保密设计等必要章节 |
| 业务背景 | ✅ | 是否清晰描述了业务背景和建设目标，是否与需求规格一致 |
| 技术架构 | ✅ | 架构风格是否说明选择理由，是否引用了 `diagrams/architecture-diagram.html`，四层结构（接入层、应用层、支撑层、数据层）是否在 HTML 图中完整呈现；4+1视图是否各自引用了独立的视图图文件（`diagrams/logical-view-diagram.html`、`diagrams/implementation-view-diagram.html`、`diagrams/process-view-diagram.html`、`diagrams/deployment-view-diagram.html`） |
| 技术栈 | ✅ | 每个技术类别是否有明确选型，选型理由是否充分 |
| 模块划分 | ✅ | 是否有划分原则、质量等级说明、模块划分表、依赖关系图 |
| 模块间接口契约 | ✅ | 是否有接口规范、具体接口定义、错误码设计 |
| 外部 PBC 能力接口 | ✅/⬜ | 若步骤6.5匹配到 PBC 能力，是否在架构文档中包含"外部 PBC 能力接口"章节，引用表是否完整（能力集、能力名称、端点、集成方式、源文件路径）；无 PBC 匹配时此项免检 |
| 数据库核心表设计 | ✅ | 是否有命名规范、核心实体ER图、核心表字段定义 |
| 部署架构 | ✅ | 是否有架构风格选择、部署方案、高可用方案 |
| 安全合规 | ✅ | 是否有安全架构、安全要求清单、合规检查项、敏感数据处理 |

**完整性问题等级**：
- 🔴 严重：必要章节缺失
- 🟡 警告：章节存在但内容为空泛描述或占位符
- 🟢 通过：章节完整且内容充实

### 3. 技术栈合规性审查

#### 3.1 公司规范合规
```
1. 前端框架是否使用 Khala-frontend-vue3 7.x
2. 后端框架是否使用 Khala-backend 7.x
3. 当 Khala 提供了 SDK/组件时，是否优先使用 Khala 组件而非自行实现或使用其他库
4. 安全组件是否使用 khala-protection-spring-boot-starter
```

#### 3.2 互斥规则校验
```
1. 是否同时使用了两个不同的关系数据库
2. 是否同时使用了关系数据库和分布式数据库（中小型项目应只选其一）
3. 是否同时使用了两个不同的消息队列
4. 是否同时使用了两个不同的对象存储
5. 是否同时使用了两个不同的分布式调度任务
6. 是否同时使用了两个不同的分布式缓存
7. 是否同时使用了两个不同的文本搜索
```

#### 3.3 业务场景适配
```
1. 电信业务是否优先选择电信或天翼云自研组件
2. 国产化要求是否选择了国产化组件
3. 通用业务无国产化要求时是否优先选择开源稳定方案
4. 中小型项目是否遵循单一性原则（如只选一种数据库）
5. 大型项目且有高并发大数据量时才考虑分布式数据库
```

#### 3.4 部署架构合理性
```
1. 部署方式是否与技术栈匹配
2. 容器化方案是否合理
3. 环境规划是否完整（Dev/Test/Prod）
```

**合规性问题等级**：
- 🔴 严重：违反公司强制规范（如未使用 Khala 框架、违反互斥规则）
- 🟡 警告：选型理由不充分、未优先使用公司推荐组件
- 🟢 通过：技术选型合规

### 4. 模块划分合理性审查

#### 4.1 划分原则
```
1. 每个模块是否遵循单一职责原则
2. 模块间职责边界是否清晰，有无职责交叉
3. 模块是否可独立开发、测试和部署
4. 模块内技术栈是否统一
```

#### 4.2 依赖关系
```
1. 模块间是否存在循环依赖
2. 模块间是否存在相互依赖（应单向依赖）
3. 依赖关系图是否与模块划分表一致
```

#### 4.3 质量等级
```
1. 每个模块是否标注了质量等级（S/A/B）
2. 质量等级标注是否合理：
   - S级：核心模块，涉及资金、用户隐私，不可出现异常
   - A级：关键模块，面向用户服务、影响SLA
   - B级：标准模块，内部使用、标准CRUD
3. 质量等级与模块职责是否匹配
```

#### 4.4 与需求规格对齐
```
1. 需求规格中的每个功能点是否都有对应模块负责
2. 是否存在需求规格未提及的冗余模块
3. 模块划分是否覆盖了所有业务场景
```

**模块划分问题等级**：
- 🔴 严重：循环依赖、职责交叉、需求覆盖缺失
- 🟡 警告：质量等级不合理、依赖关系不够清晰
- 🟢 通过：模块划分合理

### 5. 接口契约规范性审查

```
1. 接口协议选择是否合理（优先RESTful API）
2. 接口路径是否包含版本号（如 /api/v1/xxx）
3. 请求参数和响应参数是否定义完整
4. 错误码是否定义完整且有处理建议
5. 认证方式是否明确
6. 限流策略是否标注
7. 模块间接口汇总表是否完整
```

**接口契约问题等级**：
- 🔴 严重：接口定义缺失、协议选择不合理
- 🟡 警告：参数定义不完整、错误码缺失
- 🟢 通过：接口契约规范

### 6. 数据库设计合理性审查

```
1. 表命名是否遵循 {模块前缀}_{业务实体} 规范
2. 字段命名是否遵循 {类型前缀}_{实体属性} 规范
3. 核心实体ER图是否与核心表设计一致
4. 主键、外键约束是否定义
5. 索引设计是否合理
6. 分库分表策略是否适用（仅大型项目需要）
7. 数据同步策略是否明确
```

**数据库设计问题等级**：
- 🔴 严重：命名规范违反、核心表缺失
- 🟡 警告：索引缺失、约束不完整
- 🟢 通过：数据库设计合理

### 7. 安全合规完整性审查

```
1. 身份认证方案是否明确
2. 访问控制方案是否明确（RBAC/ABAC）
3. 数据传输加密是否要求 TLS 1.2+
4. 数据存储加密是否要求 AES-256
5. 敏感数据处理是否合规（脱敏展示、加密存储）
6. 密码策略是否满足最低要求（8位、复杂度、有效期等）
7. 接口安全是否覆盖（防SQL注入、防XSS、防CSRF、签名校验、防重放）
8. 合规检查是否覆盖（网络安全法、等保2.0、行业规范）
9. 审计日志是否要求
```

**安全合规问题等级**：
- 🔴 严重：安全要求缺失、敏感数据未脱敏、合规检查缺失
- 🟡 警告：部分安全措施未明确实现方式
- 🟢 通过：安全合规完整

### 8. 一致性审查

```
1. 业务背景与需求规格是否一致
2. 技术栈选型与技术架构是否一致
3. 模块划分与接口契约是否一致（接口汇总表中的模块名与模块划分表一致）
4. 数据库表与模块是否对应
5. 部署架构与技术栈是否匹配
6. 安全合规要求与质量等级是否匹配（S级模块应有更严格的安全要求）
7. 概要设计文档中模块描述是否完整一致
8. PBC 引用一致性：若存在 PBC 能力引用，检查架构文档中的"外部 PBC 能力接口"章节与版本目录增量设计文档中的 PBC 引用是否一致，且每条引用标注的 PBC 源文件路径真实存在；无 PBC 匹配时此项免检
9. design-overview.md 中的视图图链接是否与 diagrams/ 目录下实际文件一一对应
10. design-overview.md 中的功能模块索引是否覆盖所有已有模块
```

**一致性问题等级**：
- 🔴 严重：关键信息前后矛盾
- 🟡 警告：描述不一致但不影响理解
- 🟢 通过：内容一致

## 当场修改流程

### 修改触发条件
- 存在 🔴 严重问题：**必须修改**
- 存在 🟡 警告问题：**建议修改**，询问用户是否修改

### 修改步骤

1. **展示评审报告**：向用户展示完整的评审报告
2. **确认修改范围**：
   - 如果有严重问题，告知用户必须修改
   - 使用 AskUserQuestion 工具询问用户：
     - "评审发现 N 个严重问题和 M 个警告问题。是否需要修改？"
     - 选项：修改全部问题 / 仅修改严重问题 / 暂不修改
3. **逐项修改**：
   - 对于每个需要修改的问题，展示问题描述和建议修改方案
   - 修改 `khala-spec/rd/design/changes/` 目录下的设计文档
4. **重新验证**：
   - 修改完成后，重新执行步骤 2-8 的审查
   - 确认修改后的问题已解决
   - 如有新引入的问题，继续修改
5. **最终确认**：
   - 展示修改后的评审结果
   - 确认所有严重问题已解决

### 修改原则
- 修改应保持文档整体一致性
- 修改技术栈时需同步更新相关章节（技术架构、部署架构等）
- 修改模块划分时需同步更新接口契约、数据库设计
- 每次修改后验证修改是否引入新问题

## 评审结果判定

| 结果 | 条件 |
|------|------|
| ✅ 通过 | 无严重问题，警告问题 ≤ 3 个 |
| ⚠️ 有条件通过 | 无严重问题，警告问题 > 3 个 |
| ❌ 不通过 | 存在严重问题 |
